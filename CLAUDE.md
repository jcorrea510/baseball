# CLAUDE.md - Sandlot

Browser baseball batting game ("spiritual successor to the old doodle baseball game", far more polished). **Vite + vanilla JS + three.js.** Everything (textures, sounds, people, crowd) is generated in code - there are no asset files. The owner does not code: they judge by playing, so keep commands and explanations plain-English and never leave TODOs.

## Commands
- `npm run dev` - dev server (http://localhost:5173)
- `npm test` - Vitest (`tests/*.test.js`, pure logic, no browser)
- `npm run build` - production build to `dist/`. The base path comes from `scripts/resolveBase.mjs`: `BASE_PATH` if set (the GitHub workflow sets it to `/<repo>/`), `/` on Vercel/Netlify/Cloudflare Pages/Render, `/<repo>/` when `GITHUB_ACTIONS` is set, otherwise `./` (relative, works from any folder). `vercel.json` holds the Vercel settings.
- `npm run smoke` - (after a build) serves `dist/` like GitHub Pages and drives headless Chrome: must reach the title screen and survive a real click-through (Play, how-to, a setting, Quick Game, pause, a switch, resume); it also builds the game the Vercel way (served at `/`) and the default way (served from another folder) and must reach the title screen in each; with WebGL blocked, with the raw un-built source, and with a build made for the wrong base path it must show the on-screen error screen (which must not mention GitHub unless the host is `*.github.io`). `CHROME_PATH=/path/to/chrome` picks the browser locally; CI uses the runner's Chrome. It runs in the deploy workflow before publishing.
- `npm run sim` / `node scripts/sim.mjs [games] [timingSdMs] [difficulty]` - headless bot playtest with stats (win %, AVG, HR, outcome table by contact grade). Use it after changing physics/fielding/contact numbers.
- `node scripts/pitchmix.mjs [pitches]` - where the computer pitcher throws, per difficulty (share of strikes, hittable, out of reach, in the dirt, high heat...).
- `node scripts/hrrate.mjs [swings] [derby|quick]` - home run % for perfect and good swings by level (straight / pulled / opposite, early vs late). Derby targets: perfect ~70-85%, good ~25-40%; `tests/hrrate.test.js` guards the bands. Derby-only batting help lives in `modes.derby` (`evBonus`, `goodQuality`, `goodLaunch`, `pullBonus`) and reaches `computeContact` through `derbyBatting(cfg)` - the Quick game numbers are separate.
- `node scripts/umpirewav.mjs [folder]` - renders every umpire call to .wav files (for listening or analysis outside the game).
- `node scripts/wallcheck.mjs [plays]` - plays thousands of deep balls through the fielding planner and reports any fielder outside the ballpark.
- `node scripts/tune.mjs [samples] [sdMs] [difficulty]` - hit/out/HR rate by batted-ball type (for tuning fielders).
- Deploy: push to `main` -> `.github/workflows/deploy.yml` runs tests + build + publishes to GitHub Pages (Settings -> Pages -> Source: GitHub Actions).

## Architecture (three layers)
1. **Logic (no graphics, unit tested)** - `src/game`, `src/physics`
2. **Presentation** - `src/render` (three.js), `src/audio`, `src/ui` (DOM)
3. **`src/app.js`** wires them together. `src/config.js` holds ALL tunable numbers.

### Coordinates (used by every module)
Feet. Origin = back tip of home plate. `+x` = right-field side (screen-right from behind the plate), `-z` = toward the pitcher / center field, `+y` up. Spray angle 0 = center, negative = left field. The camera sits behind the plate at `+z`. Person-local axes: `+z` = the way they face, `+x` = their LEFT hand.

### Logic (`src/game`, `src/physics`)
- `physics/field.js` - bases, fence curve, fair/foul test, grandstand profile.
- `physics/pitch.js` - `buildPitch`: a pitch is a constant-acceleration path solved to hit a chosen spot at the timing plane (`pitch.contactZ`). Movement (break/hop) is visible from release.
- `physics/ballistics.js` - `simulateBattedBall`: fixed-step (1/240 s) flight with gravity, drag, backspin lift, sidespin hook, bounces, rolling, wall, stands. Returns samples; the picture replays them (frame-rate independent). Also `judgeFairFoul`.
- `game/timing.js` - timing windows (perfect/good/early/late/miss) and `resolveSwingTimes`. **Error = bat time - ball time (ms)**. The visual contact time is clamped near the ball so bat and ball always meet.
- `game/contact.js` - pitch location + timing -> exit velocity, launch angle, spray, spin.
- `game/fielding.js` - `planPlay`: given the ball flight + runners, decides catch / groundout / hit / extra bases / double play / sac fly and returns a **plan** (a timeline: fielder paths, throws, carries, runner moves, events, `endTime`). Nothing in it is random (repeatable). `createDefense` holds fielder speed/reaction.
- `game/rules.js` - counts, outs, walks, force advancement, `applyPlay`, innings, extra innings (runner on 2nd), walk-offs, line score. Pure functions on a state object.
- `game/pitcherAI.js` - what to throw (type mix by difficulty/count, tells) and where: each pitch is 'heart' (in the zone), 'edge', 'chase' (tempting, out of the zone) or 'waste' (way out of reach: in the dirt, high heat, way off the plate); `difficulty.<level>.locations` are the odds, the count shifts them (strikes with three balls, chase pitches with two strikes), and every kind of pitch misses the way it moves (a slider aimed off the plate starts as a strike and breaks out). Derby is all hittable. `node scripts/pitchmix.mjs` prints the resulting mix per level (strikes / hittable / weak-only / unhittable / clearly out). `game/aiHalf.js` - the computer's half-inning, simulated instantly from odds in config.
- `game/engine.js` - **the orchestrator**: phases `ready -> windup -> pitch -> (play) -> result -> ...` (the next windup also waits for `fieldersSetAt`: when a play ends the engine works out, from the plan, when the pitcher and catcher are back on their spots (`fielderBackTime`, using the same jog the renderer shows) plus `pace.pitcherSet`; show-only support runs are capped to the length of the play so this stays quick), swing handling (`swingPressed(sinceUpdate)` - pass the seconds between the last update and the real input event so timing ignores frame rate), Quick/Derby/Practice rules, events (`on('contact')`, `'playEvent'`, `'result'`, ...). `engine.pitchOverride` lets tests throw exact pitches.
- `game/progression.js` - localStorage (always try/catch, in-memory fallback), career stats, high scores, unlock milestones. `game/teams.js` - original teams/uniforms/bats/names. `game/bot.js` - test bot.

### Presentation
- `render/scene.js` renderer + adaptive resolution; `environment.js` sky/sun/fog/day-dusk-night presets + clouds; `stadium.js` (+ `perimeter.js`, `crowd.js`, `scoreboard.js`, `textures.js`) the ballpark; `rig.js` person model + two-bone IK (parts merged into few meshes); `poses.js` procedural animation; `actors.js` drives every person and the ball from engine state; `cameraRig.js` broadcast camera (batter view -> follow -> snap back, shake); `ball.js` ball + trail; `effects.js` particles/fireworks.
- `audio/audio.js` - Web Audio synthesis (bat crack scaled by contact quality, glove pop, crowd, cheers, organ riff). Context is created only after the first user gesture.
- `ui/ui.js` + `style.css` - all menus/HUD. `app.js` - input, time control (hit-stop, slow-mo, fast-forward), engine->effects/audio/UI hooks.

### Fielder movement and diving
- `game/fielderMotion.js` (pure logic) is the ONE movement model. `covered`/`timeToCover` (a fielder heading for cruise speed vc covers vc*(t - A*(1-e^(-t/A))) ft, A = `fielding.accel`) are used both by the planner's "can he get there?" search and by `planRun`, which the renderer plays back - so what the planner promises is exactly what is drawn. `planRun` = react, accelerate, cruise, brake; with time to spare he arrives early and waits, on a tight play he arrives on time at speed and eases to a stop past the spot (a running catch). `Mover` (braking curve, arrival radius, retarget threshold) drives everything that is not a planned run (jogging back).
- `planPlay` gives every fielder a job: `plan.paths[pos]` = his runs in order; `plan.fielderMoves` keeps one entry per run (with `role`: catch/field/cover/relay/backup/shade/watch). Backups, base coverage and pitcher/catcher roles are added in `addSupport` (movement only, never changes outcomes); `settleThrows` points each throw at where its receiver really is; `fielderFreeTime(plan, pos)` says when he may jog home.
- A dive (`planDiveRun`) only happens when the ball is just beyond running reach (`need > avail` but within `diveExtra`) AND no fielder could simply run to it within `fielding.dive.preferRun` seconds. He sprints straight at the ball (one committed direction), launches `dive.airTime` before the glove meets it, lands, slides, lies there, gets up. A fielder who dove throws later (`dive.throwExtra`). Plan events `dive` (launch), `diveLand`, and `catch`/`field` with `dive:true` drive the highlight (slow motion, dust, "DIVING CATCH!").
- The wall: `physics/field.js` has the ballpark outline (outfield wall + foul-territory walls + backstop): `isInsideField`, `clampToField(x, z, margin)`, `distanceToWall`, `wallClearance`. Every run target is pulled back inside by `fielding.wallMargin` (`addMove`); `planRun`/`planDiveRun` take `limitS` (how far he may travel before the wall) and brake harder - or start slowing earlier - so he stops in front of it (`wallBrake`); `sampleRun` also clamps to `limitS`. Home-run watchers stand a few feet in front of the wall. Anything that moves a person by other means (the jog-home `Mover`) has a `bound`. In the renderer a fielder whose play has ended finishes his planned run before the jog takes over (`st.tail`) - handing him over at full speed used to carry him through the wall. `node scripts/wallcheck.mjs [plays]` plays thousands of deep balls through the planner and reports any fielder outside the park; `tests/wall.test.js` guards it.
- Renderer rules: facing only re-aims with a reason and turns at `fielding.turnRate`; every pose change cross-fades (`crossfadePose`); never use the ball's position as a facing target once it is in his glove.
- QA: `engine.contactOverride = () => ({exitVelocity, launchAngle, sprayAngle, backspin, hook})` forces an exact batted ball; `person.animState` names the current pose. `tests/fielderMotion.test.js` covers the run profile, mover, intercept prediction and dives.

### Base runners (game/runnerMotion.js)
- ONE model for the planner and the picture: `runnerProfile(from, to, kind)` = a route (straight baselines joined by a wide circular arc at every base he keeps running through: he drifts out, touches the bag at the middle of the arc, drifts back) plus a speed profile (he gets up to speed from a standstill, `accelTime`; on a curve he can only go `sqrt(latAccel / curvature)`, so he slows into a corner and speeds up out of it; he brakes at `brake` to stop on the last bag). `runnerArrival` / `runnerFinish` give the planner every arrival time (all the old `startDelay + n * per` formulas are gone); `runnerState(move, t)` is what the renderer draws (position, heading, speed, acceleration, sideways acceleration). The numbers in `config.runner` were calibrated so arrival times match the old constant-speed model within ~0.1 s (`tests/runnerMotion.test.js` guards it, and the simulator's win%/AVG/extra-base counts are unchanged) - if you change them, re-run `node scripts/sim.mjs 120 30 pro` and compare.
- A batter who is out at first runs THROUGH the bag (`kind 'through'`), started a touch later so he touches it exactly when the planner assumed. Home-run moves carry `trot: true`. A runner who stays put waits at his lead-off spot (`leadSpot`, also where he is drawn before the pitch).
- Renderer: `runnerPoseFrame` (waiting -> lead pose, running -> `runPose` with lean/bob/arm drive from his acceleration and turning, braking, slide when `wantsSlide` (a close play: an `out`/`safe` event at that base), sit, get up). `runPose(P, phase, speed, look, {accel, side})`; `slidePose`, `slideGetUp` in poses.js. The batter's start-in-the-box offset is added to the route and faded out (blending positions used to make him look 50% faster than his legs).

### The players (rig.js)
- Same skeleton, IK and poses as always; only the shapes changed. Torso = a V-tapered lathe carrying the jersey texture (front at u = 0.25); short jersey sleeves over the team's undershirt colour (`uniform.sleeve`) or bare arms; side-striped pants, banded stirrup socks, molded cleats; a real glove (pocket, finger stall, thumb, laced webbing) and a bigger catcher's mitt; batting gloves, wristbands and elbow guard on batters; face with eyes/brows/nose/jaw, hair colour from skin tone + number, paneled cap with button and badge.
- Parts are merged into few meshes with vertex colours; `ao` on a part bakes a little ambient occlusion at its ends. `detail` (0..1) lowers polygon counts: fielders/coaches 0.62, everybody x0.75 on phones (`Actors.detailScale`). Keep full detail for batter/catcher/pitcher/umpire - they fill the screen.
- Caution: never make one part's surface coincide with another's (z-fighting shows as dotted rings) - make the outer part a touch wider.

### The umpire's voice (audio/)
- Three ways he is heard, in this order (`AudioEngine.callUmpire`, the only entry point; it swallows any audio error and respects mute / `umpireMode` 'synth' | 'speech' | 'off'):
  1. **The owner's own recordings** (`audio/umpireFiles.js`, names in `audio/umpireNames.js`): files in `public/sounds/umpire/` named `strike`, `ball`, `strike3`, `foul`, `out`, `safe` (+ optional `ball4`; extra takes `strike_b`, `strike_c`...; `.mp3/.wav/.ogg`, any capitals). The BUILD lists the folder (`scripts/umpireFiles.mjs` -> `define: __UMPIRE_FILES__` in `vite.config.js`), so the game only fetches files that exist - never probe for missing files (that fills the console with 404s, and the smoke test forbids failed downloads). Loaded once after the first user gesture (`AudioEngine.unlock`), URLs built from `import.meta.env.BASE_URL`. A call with a recording plays it (`playFile`: a little reverb + echo); calls without one use the built-in voice. Used with the Voice setting ('synth').
  2. **The built-in voice.** `planCall(kind, voice, rng)` (pure, unit tested) lays a call out as a timeline of sounds (hiss, pop, voiced vowel with resonances + pitch contour). `renderCall(plan, rate)` (`audio/voiceRender.js`, pure JS, runs in Node) turns that into samples: a glottal pulse train (jitter, shimmer, creaky cycles) through a cascade of formant resonators that glide between sounds (each hiss/pop starts from its place in the mouth, so the transition into the vowel says which consonant it was), noise for hisses/bursts/breath. `speak()` (`umpireVoice.js`) plays the buffer through presence EQ -> compressor -> `placeVoice` (pan, reverb send, two slap-back echo taps; echoes are plain delay taps, never a feedback loop). Tunables: `audio.umpire` (`grit`, `squeeze`, `presenceDb`, `reverb`, `echo`, `level`). Do not raise `grit`/`rasp` far: distortion smears the words.
  3. **Browser voices** (`speechPlan`, `pickBestVoice`, `speakWithBrowserVoice`): phrases spoken low and slow with the best local male US voice the device has; the browser will not let a page process its voice (no echo/compression).
- Kinds: strike, strikeSwing, strike3, strike3Swing, ball, ball4, foul, safe, out. The app decides which (`App.onPitchCall`, `umpireCall`): strike three and ball four come from the engine's `pitchCall` payload (`result`); fouls from the 'landed' play event; outs from 'outCall'; close plays get a planner event `safe` (`addCalls`, `fielding.closePlay`). Derby has no calls. Gestures (`umpirePose(kind)`) always play, even with the voice off; base calls are voice only (panned), plate calls also gesture.
- Every game has one umpire character (`AudioEngine.setUmpire(seed)`): pitch/roughness/tempo; each call varies a little around it.
- QA without ears: `node scripts/umpirewav.mjs [folder] [rate] [variants] [prefix]` writes every call as a .wav. `tests/voiceRender.test.js` checks pitch, vowel resonances, that consonants are quieter than vowels and that the loudest moment of "strike" is the "-eye". The most useful check used to tune the words was a speech recognizer (pocketsphinx, a stand-in for "does it sound like the word"): with a grammar of the calls, "strike" went from 0/10 understood to 9/10 once the hiss was made quieter than the vowel and the "Steee-" was dropped. Trust measurements over guesses: an unbalanced hiss made "strike" unintelligible.
- Smoke test scenario 8 builds with a pretend recordings folder (`SANDLOT_UMPIRE_DIR`), checks the files load and play, and that nothing 404s.

### Menus and HUD (ui/ui.js + style.css)
- `style.css` starts with design tokens (color, spacing `--sp-*`, corners `--r-*`, motion `--ease/--dur`). Build every new control from `.btn` (`.ghost`, `.small`, `.wide`), `.iconbtn`, `.seg` (pick one), `.switch` (on/off), `.setrow`, `.card`, `.chip`, `.panel`. Hover effects live inside `@media (hover: hover)` so phones never get stuck hover states. Icons are inline SVG from the `ICONS` map in `ui.js` (`icon('name')`).
- Text rule: labels only. No paragraph under a header, no explanatory sentences in menus or overlays; if something needs a sentence it does not belong on screen.
- Screens: `fresh(name)` gives an empty screen; if it is already showing (a setting was tapped) it is rebuilt without replaying the entrance animation (`.still`). Anything that must animate in gets `class="rise"` and is a direct child of the screen. Settings inside screens go through `settingClick` (works for `.seg` and `.switch`).
- HUD layout (keeps overlays from ever colliding): top-left pause/mute; top-centre pitch pill, then the exit-speed readout / hint; top-right practice drawer (folded on phones); bottom-left score bug (Quick) or Derby scoreboard; bottom-centre timing meter (raised above the bug row); bottom-right aim gauge (desktop) or aim buttons at the sides (touch). Which panel shows is decided by `.hud[data-mode]` in CSS, never by inline `display`. Call banners are a compact plate; only home runs get the big celebration. Check any HUD change at 1280x720, 844x390, 568x320 (phone landscape) and 390x844 (portrait).

### Startup and the boot guard (do not bypass)
- `index.html` has an **inline classic script** (`window.__sandlotBoot`) that owns the "Warming up the ballpark" splash and the `#boot-error` screen. It works even when the game's own files never load. `done()` hides the splash; `fail(kind, err)` shows a readable error (kinds: `load`, `start`, `frame`, `timeout`). State is mirrored in `<html data-boot="loading|ready|failed:<kind>">`.
- It catches: the module script failing to load (capture-phase `error` on `<script>`), uncaught exceptions / rejected promises while starting, and a 45 s timeout (soft "still loading" note at 12 s).
- `main.js` builds the `App` inside try/catch and starts on a timer as well as on an animation frame (frames never fire in hidden tabs). `App.loop` requests the next frame first, guards each frame with try/catch, and calls `__sandlotBoot.done()` only after the first frame draws; repeated frame errors stop the loop and call `fail('frame')`.
- Never add startup work that can throw or wait without going through this path, and never remove the splash anywhere else.
- Two hosting pitfalls, both guarded by `tests/base.test.js`, `tests/boot.test.js` and `npm run smoke`: (1) a build whose base path does not match where it is served asks for `/baseball/assets/...` at the site root and 404s (this once put the Vercel site on the error screen) - never hardcode a base path, use `resolveBase`; (2) the load-failure screen must stay host-aware: players see a plain "reload" message, and only the folded Technical details carry a site-owner hint (GitHub Actions advice only on `*.github.io`).
- Deploy pitfall: GitHub Pages must be set to **Source: GitHub Actions**. "Deploy from a branch" publishes the repo's raw `index.html` (pointing at `/src/main.js`, which does not exist on the site) - that once left the live game on the splash forever. `tests/boot.test.js` and `npm run smoke` guard this.

## Conventions
- Put every tunable number in `src/config.js` with a plain-English comment. No magic numbers in logic.
- Logic modules must not import three.js or touch the DOM (so Vitest and `scripts/sim.mjs` can run them in Node).
- Timing must never depend on frame rate: use engine time and `swingPressed(sinceUpdate)`; physics is precomputed at fixed steps.
- Renderers read engine state; they never change game outcomes.
- After changing physics/fielding/contact numbers: run `npm test` and `node scripts/sim.mjs 100 30 pro` and check win% / AVG still look sane (skilled bot sd 20-30 ms wins ~85-95% on Pro; sloppy sd 70 ~55-60%; All-Star is clearly harder).
- QA hooks: `?mode=quick|derby|practice&bot=1&sd=25&seed=7&tod=night` starts a game immediately (bot plays); `window.__app.tick(dt, render)` steps the simulation without waiting for real time (used by headless-browser QA).
- Commit messages: clear, one milestone/topic each.
